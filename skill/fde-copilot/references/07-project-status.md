## 4. 已知问题：视觉风格（AI design slop）

**用户反馈**：整体风格"太平铺直叙、没有层次感、AI 味太重、拿不出手"。

**关键判断（已验证）**：**这不是参数问题。** 已调过一轮配色、间距、阴影、字号、动效，用户反馈"基本没变化"。

**根因（有据可查）**：这是 2026 年被专门命名的现象——**AI design slop**。原理是"分布收敛"：模型从训练数据的统计规律预测，那些普遍安全、不得罪任何人的选择占据训练数据主流，模型不断退回这些安全选项（紫色渐变、居中大标题、三张卡片一排、hover 弹跳）。代码生成层会进一步收窄到最容易实现的东西。

**行业公认的解法**：**不能靠"再好看点"这类抽象形容词**——如果模型已经把每一个好看的界面和一百万个平庸的界面平均在一起了，更好的提示词也没用。**必须给一个具体的、风格鲜明的参照系**（如"做成 Linear 那种"）。

**下一轮视觉迭代的正确做法**：
1. **先选定风格参照**（Linear / Notion / Stripe / Apple HIG / Google Material / aTool 的德勤绿深色系，都可以）
2. **看过真实截图、确定自己喜欢**，再动手
3. 把具体参照写进指令，而不是"专业、有层次"这类词

**aTool 的设计系统（可直接抄的规格）**：
- 品牌色：德勤绿 `#86BC25`（亮版 `#B0E057`）+ 青绿 `#2DD4BF` 点缀
- 深色四层递进：`#0B0D12`（页面底）→ `#10131A` → `#14171F`（卡片）→ `#1B1F2A`（浮起元素）
- 阴影三档 + 品牌色发光阴影：`0 0 0 1px rgba(157,212,59,.32), 0 8px 24px rgba(157,212,59,.18)`
- 文字三级灰：`#ECEEF3`（主）/ `#9AA3B7`（次）/ `#5F6985`（弱）
- 背景网格点：`rgba(255,255,255,.04)`

**⚠️ 但 Maggie 从未说 aTool 风格是最好的标准**，这只是可选参照之一。

## 5. 协作方式（务必遵守）

这些是 Whisper 在协作中反复强调、且 Claude 多次违反后被纠正的：

### 🔴 绝不虚报
汇报中**只写用户实际做过的事**。Claude 执行的部分要如实写成"审核确认"而非"我做了"。

**已发生的错误示例**（引以为戒）：
- Claude 曾把"Claude 走了一遍七步方法"写成"用户跑了一遍七步方法" → 用户强烈反弹："我的2根本就没做啊，你干嘛总是乱给我加戏呢"
- Claude 曾把 As-is/To-be 泳道图（旧项目内容）带进新项目 → 用户："我得和你说清楚这个项目和之前完全分开，你直接忽略？"

### 🔴 判断权在用户
Claude 负责**追问与落笔**，不替用户下结论、不替用户产出他该判断的内容。用户明确要求："要确保东西是我既定的成果，不是你 AI 现场给我分析的，不然没有可复制性"。

**正确分工**：Claude 可以做体力活（从材料里挑出痛点原文、整理成正式表达）；用户做判断活（这条对不对、要不要用、砍哪条）。

### 🔴 稳扎稳打，不赶进度
用户明确要求高质量高精度，不接受为赶时间牺牲质量。Claude 多次因为"急着推进下一步"被批评："你到底在急什么，你稳扎稳打，把每个地方每个细节都落实啊"。

### 🔴 不打比方绕圈
用户不喜欢餐厅/厨房/网盘这类类比。直接说事。用户原话："别和我讲什么家餐厅的宣传册，你说这些有鬼用啊"。

### 🔴 一次一个动作
用户是 vibe coding 零基础。操作类指令必须一步一停、等确认，不能一次甩一堆步骤。

### 🔴 内容必须有出处
凡是推断，明说是推断。**曾发生 Claude 编造"提交复核""待专家审"这类 Maggie 文档里根本没有的术语**，已纠正。

### 🔴 界面数据用自己的场景
严禁照抄 techproto 的项目名、人名、客户名。

## 7. 关于 Dify 与后端的判断

**Dify 是什么**：用拖拽方式搭 AI 工作流的平台，不用写代码。

**Whisper 自己的技术判断（正确）**：
> "我的这个项目是实时的，不能依靠完成形态的文本拖动吧，而且我肯定不止 5 个节点啊"

**这个判断成立**：
- Dify 工作流是**批处理**模式（输入 → 跑完一串节点 → 输出），适合"访谈结束后提炼机会卡"
- Mission Room 是**实时**场景（每记一句回答，NBM 就要更新），每次调用都重跑整条流程会慢且贵
- 真实做法通常是：实时部分用轻量 AI 调用，批处理部分用 Dify 工作流，**不是二选一**

**但现阶段不需要设计这个**：
1. Maggie 明确说"只有前端页面，没有后端"
2. 路线图下一步是画界面，不是搭 Agent
3. **参照物 techproto 和 aTool 本身也都没有 Agent 实现**——techproto 是纯 UI/UX 原型，aTool 是产品介绍页

**⚠️ 关键澄清**：那两份参照物之所以看起来"活"，是因为**屏数多（点一下切一屏）+ 交互效果做得细（主题切换、搜索筛选、SVG 动画，都是纯前端 JS）**，与是否接 Dify 无关。**我们的页面"死"，是因为只有 1 屏、点了没地方去，不是因为没接 AI。**

## 8. 汇报的正确写法

**已验证有效的汇报结构**（给 Maggie 用）：

```
进度更新～👇
线上链接：https://fde-copilot-xi.vercel.app
仓库：https://github.com/siyuanou8/FDE-Copilot

这轮做了 N 件事：
1. [实际做的事]
2. [实际做的事]

[诚实说明不足 + 原因分析 + 下一轮打算]

下一步：
1. [具体到能验收的动作，引用 QA Gate / ADR / HANDOFF 章节]
2. ...

[需要确认的问题]
```

**要点**：
- **语气谦逊克制但不自贬**——"做得还比较粗、我自己不太满意"是判断；不写自我羞辱的话
- **诚实交代不足，但同时给出原因分析和解法**——读起来是"我知道问题在哪、我有办法"，不是"我搞砸了"
- **下一步要引用文档依据**（QA Gate 哪几条、HANDOFF 第几节、ADR 编号），证明照规矩在走
- **主动交代反直觉的地方**（比如"链接点开还是初始模板，我是先把管道打通再填内容"），抢在对方发现之前说
- **不写没做的事**，一件都不写
