## 1. 项目一句话

FDE Copilot 是面向**企业 AI 咨询项目**的 **AI-native Mission System**。它帮助顾问从行业模板和企业战略假设出发，开展多场业务访谈，从访谈证据中提炼 AI 机会卡，并进一步生成 ProcessTwin 流程图和 One Page Card 交付物。

**它明确不是**：会议纪要工具、普通流程图工具、传统多页面 SaaS。

---

## 2. 铁律（违反即返工，无例外）

1. **以 Maggie 的 PRD 为唯一口径**。PRD 定方向与边界，画板层在其框架内往下细化，不是补其不足。用户早期自拟的「七步骤」（北极星→访谈采集→场景拆解→第一性原理反问→相似案例启发→流程图重构→需求输出）**已弃用**，不再作为做事框架，避免两套语言打架。
2. **每个结论必须有来源和确认状态**。这是产品灵魂，也是画板设计的硬约束。
3. **任何非材料直接明说的判断，必须标注为推断 + 待确认**，不得当作既定事实展示。
4. **界面示例数据必须用本项目自己的场景**（如万华化学研发 AI 创新材料），**严禁照抄 techproto 的项目名、人名、客户名**。
5. **本项目与用户过往所有项目（宏观框架、AI战略分析、并购研究、郑煤机/咨询流程等）完全无关**，当白纸处理，不得引入旧项目内容。
6. **现阶段只有前端、没有后端**，页面数据均为静态写死。这是 Maggie 定的边界，不是缺陷。

## 3. 核心对象链（产品骨架）

```
IndustryTemplate → Enterprise → StrategicContext → Interview
→ Evidence → AIOpportunityCard → ProcessTwin → Deliverable
```

分三段理解：

- **准备层**（IndustryTemplate / Enterprise / StrategicContext）：解决「从零开始、漏项、多客户混淆、访谈跑偏」
- **心脏层**（Interview / Evidence / AIOpportunityCard）：真正挖价值，产品核心产出在此
- **交付层**（ProcessTwin / Deliverable）：把价值变成客户可用的成品

完整定义、归属规则、来源类型、确认状态见 `references/01-product-foundation.md`。

## 4. 画板设计标准（本项目最重要的产出标准）

对标 techproto-platform-v5 原型文档。**核心认知：差距不是屏数，是「一屏 9 样 + 多状态 + 注解」vs「只有一个标题」的深度差距。**

**每屏固定装 9 样：**

1. 画板编号 + 定级（是否核心）
2. 标题 + 一句话价值
3. 路由 URL
4. 区块摘要
5. 本版变更说明
6. 浏览器地址栏 mock + 画布尺寸
7. 带真实感数据的界面（用本项目场景数据）
8. 底部注解区（逐区块解释设计意图 + 引用规格章节）
9. 角色视角说明

**三个密度来源：** 一屏画多状态（有数据态/空状态，含空态引导文案）；标注已知实现问题；量化改进效果。

展开说明与 techproto 解剖详见 `references/03-canvas-standard.md`。

## 5. 画一屏画板的标准流程

**接到任何画板任务，按此顺序执行，不跳步。**

**第一步 · 定位。** 读 `references/04-canvas-blueprint.md` 中该屏的条目，取出三样：这屏在业务流程里干什么、依据出自哪份文档哪一节、预期有哪几个区块。跳过这步会画出定位错的东西——例如把本该是某屏内部区块的东西误做成独立页面。

**第二步 · 挖边界问题。** 打开该屏对应的 PRD 章节，逐句读，每读一句问一次「这句话没说清什么」。PRD 描述的是顺利路径，画板必须回答边缘情况：数据缺失时显示什么、冲突时如何处理、用户中途退出后回来看到什么、系统的推断如何标记。**这一步的产出是画板密度的主要来源**，不做这步画出来的就只是流程复述。典型追问方向见 `04-canvas-blueprint.md` 各屏的「边界追问方向」。

**第三步 · 查约束。** 读 `references/06-constraints.md`，摘出与本屏相关的 ADR 条目和 QA Gate 条目，列在手边。这步防止画出违反已定决策的设计——ADR 是判例法，推翻它意味着团队返工。

**第四步 · 按模板填写。** 使用 `references/08-canvas-template.md` 的骨架，不自由发挥结构。第二步挖出的边界问题填进「边界问题与判断」表，每条判断都要标依据（引用 ADR/QA Gate 编号，或明确标注「本项目判断，PRD 未覆盖」）。

**第五步 · 交付前自查。** 逐条核对第三步摘出的 QA Gate 条目，把勾选结果写进画板末尾。未通过的项不得静默略过：要么改设计，要么写进「已知问题与待补」并说明原因。

**贯穿全程的三条**：示例数据只用本项目自有场景（万华化学等），严禁照抄参照物的项目名人名；任何非文档明说的判断必须标为推断且待确认；每条结论都要能追溯到来源。

## 7. 本项目的原创设计：反向沉淀机制

PRD 中模板知识只能单向流出且无人补充（Maggie 原话：「这个现在是一个知识的空白，这块的知识确实需要有人输入」）。本项目提出**让模板从每一次真实访谈中自己长出来**，这是超出 PRD 的原创贡献。

完整机制、三屏落点、置信度计数规则、污染防护见 `references/05-reverse-sedimentation.md`。

## 8. 协作方式（务必遵守）

- **稳扎稳打，不赶进度**。用户明确要求高质量高精度，不接受为赶时间牺牲质量。
- **判断权在用户，Claude 负责追问与落笔**。不替用户下结论、不替用户产出他该判断的内容。
- **绝不虚报**。汇报中只写用户实际做过的事；Claude 执行的部分如实写成「审核确认」而非「我做了」。用户对此极度敏感，多次纠正过。
- **不打比方绕圈**。用户不喜欢餐厅/厨房这类类比，直接说事。
- **一次一个动作**。用户是 vibe coding 零基础，操作类指令要一步一停、等确认。
- **内容必须有出处**。凡是推断，明说是推断。
