## 1. ADR · 架构决策记录（13 条）

**ADR 是项目的"判例法"——定过的案子，不重审。** 因为 AI 没记忆、新人不知道历史，没有 ADR 就会把几个月前吵完的架又吵一遍，推翻已定结构导致大返工。

| 编号 | 内容 | 是否直接约束画板 |
|---|---|---|
| ADR-001 | 战略解码属于 Enterprise，不属于 Interview | ✅ P2 |
| ADR-002 | Interview 必须继承 Enterprise 的北极星指标和核心能力 | ✅ P4 |
| ADR-003 | Scenario/AI Opportunity 可聚合多场 Interview 的证据 | ✅ P6 |
| ADR-004 | IndustryTemplate 只提供默认假设，所有此类内容必须标 `to_be_confirmed` | ✅ P1/P2/X4 |
| ADR-005 | One Page Card 不是独立一级业务对象，是 AIOpportunityCard 的表达形态 | ✅ P6 |
| ADR-006 | 流程图必须由 ProcessTwin 支撑 | ✅ P7 |
| ADR-007 | **Next Best Move 是现场访谈最高优先级交互** | ✅ P4 |
| ADR-008 | 阶段级/槽位级确认摘要应绑定 Slot，**不做右侧全局模块** | ✅ P4 |
| ADR-009 | 确认过的推荐问题应作为待回答问题进入**左侧 Q&A 流** | ✅ P4 |
| ADR-010 | **Case Intelligence 必须内嵌于 Mission Room，不独立成主页面** | ✅ P4，排除 X5 |
| ADR-011 | Interview 是原始材料，不是 AI 需求本身 | ✅ P4/P5 |
| ADR-012 | AIOpportunityCard 从 Interview Evidence 推导，并承载 One Page Card 结构 | ✅ P6 |
| ADR-013 | 一场 Interview 可生成多张 AIOpportunityCard；一张卡可关联多场 Interview | ✅ P5/P6 |

**画板设计时最常踩的三条**：ADR-007（NBM 必须最显眼）、ADR-008（槽位确认不能做成右侧全局模块）、ADR-010（案例不能独立成页）。

## 2. QA Gates · 质量闸门（5 组）

**作用**：让"做完了"从主观判断变成**逐条打勾**。做完照着勾，自己能验、Maggie 也能验。

### 使用方式（这是动作，不是知识）

**画板流程第三步**：摘出本屏适用的条目，列在手边，设计时对着做。

**画板流程第五步**：交付前逐条核对，把勾选结果写进画板第六节。

**未通过项的处理**：不得静默略过。要么改设计使其通过，要么写进画板「已知问题与待补」并说明原因（例如「本屏仅一张机会卡，多卡能力待材料补充后验证」）。

**对应关系速查**：

| 画板 | 适用的 QA Gate 组 |
|---|---|
| P1 / P3 | Interview Setup QA Gate |
| P4 | Mission Room QA Gate |
| P5 / P6 | AIOpportunityCard QA Gate |
| P7 | ProcessTwin QA Gate |
| 所有涉及数据字段的屏 | Data Model QA Gate |

### Mission Room QA Gate（对应 P4）
- [ ] 顾问 **3 秒内**能看到下一个最该问的问题
- [ ] Next Best Move 出现在**右侧行动区第一屏**
- [ ] 显示：**为什么问、服务哪个北极星指标、补哪个槽位缺口**
- [ ] Case Intelligence 服务于当前问题，**不是独立案例墙**
- [ ] 候选需求描述显示**来源和确认状态**

### Data Model QA Gate（跨屏通用）
- [ ] Interview 有 `enterpriseId`
- [ ] AIOpportunityCard 有 `enterpriseId`、`sourceInterviewIds`、`sourceEvidenceIds`
- [ ] StrategicContext 属于 Enterprise
- [ ] One Page Card 不是独立一级业务对象
- [ ] IndustryTemplate 默认值标记为 `to_be_confirmed`

### ProcessTwin QA Gate（对应 P7）
- [ ] 流程是 **stage × swimlane** 网格
- [ ] 节点待在 stage/lane 单元格内
- [ ] 节点占位一致
- [ ] AI 用 **tag** 表达，不用随意颜色
- [ ] 决策节点是短问句
- [ ] 箭头正交，路径样式一致
- [ ] JSON 面板默认折叠

### Interview Setup QA Gate（对应 P1/P3）
- [ ] 新建企业只需**企业名 + 行业**
- [ ] 行业模板预填战略假设
- [ ] 战略解码**不阻塞**访谈开始
- [ ] 部门选择生成默认访谈提纲
- [ ] 默认提纲 **8 问分 3 组**
- [ ] 用户可覆盖或合并自定义问题

### AIOpportunityCard QA Gate（对应 P5/P6）
- [ ] 一场访谈可生成**多张**卡
- [ ] 每张卡带来源访谈与证据
- [ ] 每张卡有成熟度评分和状态
- [ ] 每张卡有或可关联 As-is / To-be ProcessTwin
- [ ] 卡片字段显示来源和确认状态

## 3. SKILL · 五层分类法与迭代纪律

**每次改动前必须先分层**，声明本轮改什么、明确不改什么。这是防"一锅粥乱改"的纪律。

**五层**：
1. 对象 / 数据模型层
2. 工作流层
3. UI 交互层
4. 视觉规范层
5. 工程实现层

**实际用法示例**（Mission Room 那轮实践过）：
```
【本轮只改】UI 交互层 + 视觉规范层（访谈进行页的布局与呈现）
【本轮不改】对象/数据模型层、工作流层（不碰 DATA_MODEL、不改 PRD 流程）
```

**这句话的双重作用**：写在给 AI 的指令里，它就不会乱伸手；写在给 Maggie 的汇报里，她一眼知道你有纪律。

**每轮迭代应输出的四段**（SKILL.md 规定）：
1. **Harness 判断** — 层级分类 / 修正哪个老问题 / 改哪个对象
2. **设计判断** — 为什么需要这个改动 / 它如何契合 AI-native Mission System / 影响哪些数据血缘或流程关系
3. **有边界的执行指令** — 背景 / 任务 / 约束 / 验收标准 / 要求返回格式
4. **QA Gate** — 本轮的具体检查项 / 需要的截图或构建证据

**偏好输出格式**：
- Harness 判断
- 本轮只改什么
- 本轮不改什么
- 给 Codex / Claude 的执行指令
- QA Gate
- 下一轮建议

## 4. Anti-patterns · 反面清单

SKILL.md 明令避免（这些是前人踩过的坑）：

- ❌ 给 AI 下"愿景式大指令"却没有验收标准
- ❌ 让 AI 一次改多个核心对象
- ❌ 给"本该嵌在流程里的概念"单开页面
- ❌ 做没有数据血缘的 UI 卡片
- ❌ **让 "AI-native" 变成"加更多分析面板"**（这条最狠：AI-native ≠ 多摆几个 AI 卡片）
- ❌ 把行业默认值当成客户已验证的事实
- ❌ 让一页纸输出脱离源证据

## 5. CODEX 执行规范

**这是防 AI 闯祸的护栏，动代码时天天用。**

**改之前必须：**
1. 读 AGENTS.md 和 docs/* harness 文件
2. 分类改动层级
3. 说明本轮修改的单一核心对象
4. 说明可能改到哪些文件
5. 明确非目标

**改的时候禁止：**
- 删关键文件
- reset Git
- commit 或 push（需用户确认）
- 连接真实 API 或付费服务
- 改无关模块

**改完必须返回：**
- 改动摘要
- 变更的文件
- 数据模型变化
- UI/流程变化
- `npm run build` 结果
- QA Gate 检查结果
- 遗留问题

## 6. HARNESS · 每轮迭代必答五问

任何产品或代码改动前，先回答：

1. **这轮改的是哪一层？**（对象/数据模型层、工作流层、UI 交互层、视觉规范层、工程实现层）
2. **在修正哪个反复出现的问题？**
   - 页面碎片化
   - 数据归属错误
   - AI-native 被降级成卡片/面板
   - 顾问看不清下一步
   - 证据/来源不可追溯
   - 流程图不专业或没有结构
   - One Page Card 与证据脱节
3. **这轮的单一核心对象是什么？**
4. **明确不改什么？**
5. **QA Gate 是什么？**

**开发原则**：渐进式本体 + 垂直切片
- 快速做出一个能用的垂直切片
- 让 demo 暴露结构问题
- **一旦出现结构问题，停止加功能，先夯实数据模型 / ADR**
- QA Gate 通过后再继续

## 7. 新成员上手五步

来自 HANDOFF 第 8 节（docx 版为 5 步，md 版为 4 步，以 5 步为准）：

**第一步：先读 PRD 和 DATA_MODEL，理解对象关系**
→ 防"不懂骨架就动手"。界面是数据结构的表皮，骨架没搞懂就画页面，画出来跟底层对不上。

**第二步：读 ADR，避免重复推翻已确认结构**
→ 防"重开旧战"，这是最省时间的一步。

**第三步：修改前使用 SKILL.md 进行层级判断**
→ 防"一锅粥乱改"。

**第四步：每轮只改一个核心对象，并用 QA_GATES 验收**
→ 防"贪多 + 做完不知道对不对"。

**第五步：需要开发时，按 CODEX_EXECUTION_HARNESS 生成小步任务**
→ 防 AI 闯祸。**关键词是「小步」**：不是"帮我做个访谈页面"（愿景式大指令，SKILL.md 明令禁止），而是"在 X 文件里加一个右侧栏组件，显示这三个字段，不动其他模块"。

**这五步串起来是一条漏斗**：先懂骨架 → 别推翻旧决定 → 分层划界 → 一次一个+验收 → 小步喂给 AI。

## 附：整套文件体系的哲学

**人定"做什么"和边界（PRD/原则/ADR），AI 负责"怎么实现"，QA Gate 负责验收。人拍板，AI 执行，文档是它俩之间的合同。**

⭐ **一个值得在汇报时提的观察**：这跟产品本身的理念一模一样——Copilot 不是 Autopilot，human on the loop。**团队管 AI 写代码的方法，和产品里管 AI 做访谈的方法，是同一套哲学。**
